# Сценарий защиты Musico

Черновик на 7–10 минут для подготовки Week 15–16. Перед выступлением открой проект на устройстве, выполни сценарий самостоятельно и замени места в квадратных скобках фактическими результатами. Не заявляй о функциях, которые не проверил на устройстве.

## Рассказ и демонстрация

### 0:00–1:00 — тема и задача

«Мой проект — Musico, тема 19: музыкальный плеер. Приложение объединяет каталог композиций, поиск, воспроизведение, пользовательские плейлисты, избранное и историю. Основная аудитория — слушатели, которым нужно хранить свою музыкальную библиотеку и продолжать работу с ней после входа с другого устройства. В качестве аналогов я изучал Spotify, YouTube Music и Apple Music; мой учебный MVP сосредоточен на базовом цикле “найти — включить — сохранить в библиотеку”.»

Покажи главную страницу и кратко назови разделы: каталог, поиск, библиотека, аккаунт, экран плеера, площадки и уведомления.

### 1:00–2:30 — слои и состояние

«Код разделён на presentation, domain и data. Экраны находятся в presentation; domain содержит сущность площадки, контракт репозитория и сценарий загрузки; data реализует Supabase и локальный кэш. Репозиторий скрывает детали источника данных, а Provider передаёт его зависимым экранам.»

«Provider оставлен для простого состояния каталога и темы. Для команд воспроизведения используется PlaybackCubit: это отдельный поток событий с предсказуемыми состояниями play/pause/loading. `setState` подходит для локальных состояний одного виджета. InheritedWidget — низкоуровневый механизм передачи зависимостей; Provider сокращает шаблонный код. BLoC/Cubit уместен там, где важны явные переходы состояний.»

Открой `lib/main.dart`, затем покажи `lib/data/music_repository.dart`, `lib/features/player/playback_cubit.dart` и `lib/providers/music_data_provider.dart`. Объясни, как данные проходят от экрана к репозиторию и обратно.

### 2:30–4:00 — пользовательский сценарий

Выполни на экране:

1. Найди композицию через поиск.
2. Запусти её и перемотай воспроизведение.
3. Добавь трек в избранное.
4. Создай плейлист и добавь в него трек.
5. Открой библиотеку и покажи историю.
6. Отключи сеть и покажи доступный каталог из локального кэша.

«Для входа используется Supabase Auth. Пользовательские записи хранятся в Postgres и защищены Row Level Security. Firebase-клиент в приложении не используется. Публичный ключ Supabase предназначен для клиента; привилегированные ключи остаются только на сервере.»

### 4:00–5:00 — навигация, адаптация, карты

«GoRouter задаёт именованные маршруты, параметры трека/плейлиста и индексированный shell для вкладок. Redirect защищает библиотеку и аккаунт от неавторизованного доступа. Адаптивные сетки изменяют число колонок при увеличении ширины.»

Открой площадки, покажи список и карту при настроенном Maps API key. Нажми на определение местоположения и объясни, что разрешение запрашивается только по действию пользователя. Если ключ или реальные записи ещё не настроены, прямо покажи состояние-заглушку и не называй карту полностью подключённой.

### 5:00–6:00 — локальные данные и платформа

«Настройка темы сохраняется через SharedPreferences. Hive хранит каталог, избранное и историю для работы при временной потере сети. Для Android реализован собственный MethodChannel: экран аккаунта запрашивает уровень заряда батареи у Kotlin-кода.»

На Android устройстве покажи заряд батареи. Если проверяется только эмулятор, так и скажи. Для фонового воспроизведения отдельно проверь, что музыка продолжает звучать после блокировки экрана, а системное уведомление позволяет управлять playback. Вставь сюда фактический результат проверки: [результат на устройстве].

### 6:00–7:30 — тесты, CI и производительность

«Unit-тесты проверяют репозиторий, кэш и логику воспроизведения; widget-тест проверяет отображение ключевого компонента; integration-тест проходит по главной странице и поиску. Локальный отчёт показывает [актуальный процент из `./tool/check_coverage.sh`]. GitHub Actions запускает форматирование, анализ, тесты и сборку APK при push и pull request.»

Покажи свежий green run CI и APK artifact после push в репозиторий. Открой DevTools Performance/Memory и покажи собственные замеры до/после: [добавить frame time и memory из реального профилирования]. Не заменяй этот шаг числом из документации или оценкой.

### 7:30–8:30 — ограничения и публикация

«Схема Supabase и серверная функция отчёта ошибок хранятся в репозитории. Сначала я разворачиваю миграцию, настраиваю OAuth и push credentials, затем проверяю RLS на облачном проекте. Для Google Play нужны уникальный package id, приватный upload keystore, подписанный AAB и заполненные материалы магазина. Уведомления в текущем MVP — это Supabase inbox; доставка на заблокированное устройство требует отдельного APNs/Android push transport.»

Покажи только готовые артефакты: [подписанный AAB, публичная политика, реальные скриншоты, ссылка на CI и профилирование]. Если какого-то пункта ещё нет, назови его незавершённым.
