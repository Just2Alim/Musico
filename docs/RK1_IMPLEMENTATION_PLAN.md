# План закрытия требований РК1

**Цель:** довести недели 1–7 проекта Musico до проверяемого состояния и перечислить локальные препятствия, которые требуют действий владельца устройства или облачного проекта.

**Архитектура:** сохранить текущий Flutter/Supabase проект и закрыть пробелы небольшими изолированными изменениями. Учебные варианты управления состоянием демонстрируются на одной функции избранного; основная архитектура приложения продолжает использовать Provider и Cubit/BLoC.

**Технологии:** Flutter/Dart, Provider, flutter_bloc, get_it, Supabase REST/JSON, Hive, SharedPreferences, GoRouter и flutter_test.

**Источник требований:** `individual_project_flutter_ru.docx`, недели 1–7; РК1 оценивается по этим неделям.

## Область

- Неделя 1: Dart задачи, README и состояние Flutter toolchain.
- Неделя 2: ключевые экраны, Material 3 и эскизы.
- Неделя 3: setState → InheritedWidget → Provider для избранного и сравнение подходов.
- Неделя 4: BLoC/Cubit, слои, Repository и get_it для внедрения зависимостей.
- Неделя 5: Supabase REST/JSON, модели, состояния запроса, поиск и обновление.
- Неделя 6: SharedPreferences, Hive и offline fallback.
- Неделя 7: GoRouter и адаптивность телефона/планшета и ориентаций.

## Ограничения проверки

- Не принимать юридические лицензии Android SDK от имени владельца.
- Не использовать переданный ранее привилегированный Supabase secret; применять только publishable key в клиенте.
- Для удалённых изменений сначала проверить целевой Supabase-проект и его существующие данные; не использовать привилегированные ключи в клиенте.
- Для адаптивности использовать автоматические тесты размеров; реальные скриншоты на устройстве остаются отдельным подтверждением.

## Порядок работы

1. Сохранить исходный статус и проверить существующие тесты.
2. Добавить тестируемую демонстрацию этапов управления избранным, включая собственный InheritedWidget.
3. Добавить get_it как контейнер DI приложения и тест регистрации зависимостей.
4. Закрепить JSON mapping и сетевые состояния тестами; не объявлять живой backend проверенным без удалённой схемы.
5. Добавить widget-проверки ключевых размеров и ориентаций; исправить обнаруженные переполнения.
6. Обновить README и матрицу РК1 с результатами и внешними блокерами.
7. Запустить форматирование, анализ, тесты, сборку и повторно проверить `flutter doctor`.
